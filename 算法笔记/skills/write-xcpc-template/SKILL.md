# 编写 XCPC 模板

## 准备上下文

1. 读取 [references/style-guide.md](references/style-guide.md)，按其中的格式和语言基线写作。
2. 在现有仓库中工作时，先读取目标文件及同目录下 2 至 4 份相近算法笔记；以目标文件、相邻文件、风格基线的顺序解决格式冲突。
3. 新建单算法 Markdown 笔记时，以 [assets/algorithm-note-template.md](assets/algorithm-note-template.md) 为骨架，并删除所有占位内容。
4. 仅在缺少会影响正确性的约束时提问；对命名、标签数量和标题层级作保守推断。

## 选择输出形态

- 默认生成“单算法笔记”：包含 frontmatter、算法名、定义、实现、代码和例题链接。
- 用户只要“代码模板”或“板子”时，输出可直接复制的 C++ 组件；不强行添加 Markdown 笔记外壳。
- 用户明确要求 Codebook 页时，使用“作用、核心思想、标准代码、复杂度、易错点”结构，只保留一个最稳的赛场版本。
- 用户要求修改现有笔记时，保持原有标题层级和相邻笔记风格，不做无关重排。

## 编写内容

1. 用 1 至 3 句话说明用途、适用条件和关键结论。
2. 用一小段或不超过 5 个步骤说明状态、不变量、转移或维护方式。
3. 明确写出时间复杂度、空间复杂度以及复杂度中的变量含义。
4. 只在算法存在实质性取舍时保留多个实现；分别用“朴素实现”“堆优化实现”“倍增实现”等标题命名。
5. 使用简洁中文、标准数学公式和反引号标记代码标识符；删除历史背景、重复总结和教程式铺垫。
6. 不编造例题链接。没有可靠链接时保留空的“例题链接”小节，或在用户允许时省略。

## 编写代码

1. 默认使用 C++20 和仓库内常见的竞赛命名；优先使用 `struct`、`vector`、构造函数或 `init`，并提供必要的 `add`、`merge`、`query`、`run` 等接口。
2. 对可复用组件只给组件本体；对完整解题框架才添加 `solve()` 和 `main()`。
3. 明确下标从 0 还是 1 开始、输入是否允许负权或重边、空集合如何处理，以及 `INF`、乘法和加法是否可能溢出。
4. 只为不变量、回滚、边界和非直观操作添加短注释，不注释显然的语句。
5. 不默认使用 `#define int long long`、全局超大数组或未解释的魔法常量；根据数据范围选择 `int`、`long long` 或 `__int128`。
6. 保证代码块依赖完整。对 `assert` 等工具显式包含对应标准头文件，不依赖聚合头的间接包含；若组件依赖外部类型、常量或预处理，必须在代码前一句说明。

## 维护当前算法笔记仓库

- 优先修改原始分类目录中的 Markdown 笔记。
- 将 `ACM知识库/`、`XCPC赛场Codebook.md` 视为生成产物；除非用户明确要求，不直接手改生成文件。
- 需要同步知识库或 Codebook 时，先修改源笔记或对应生成脚本，再运行仓库现有构建命令。
- 保留用户已有内容和未提交改动，只修改任务范围内的文件。

## 校验

1. 对 Markdown 产物，使用可用的 Python 3 解释器运行本 skill 目录中的 `scripts/check_xcpc_note.py <文件> --mode note`；Codebook 单页改用 `--mode codebook`。修复所有 error，并判断 warning 是否符合目标文件的既有格式。
2. 检查 Markdown 围栏成对、C++ 代码块非空、标题层级连续、公式闭合、链接真实。
3. 对独立程序执行 `g++ -std=c++20 -Wall -Wextra -fsyntax-only`。对组件创建最小临时包装进行同等语法检查；完成后删除临时文件。
4. 用最小样例、边界样例和一个针对算法前提的反例手动走查。
5. 最终只简要说明生成或修改了什么、验证结果和仍需用户补充的内容。
